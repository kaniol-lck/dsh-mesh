# 典型环境与降级方式

先认领你的环境，再看它能做到什么、会退化成什么样。所有示例用占位符：
`<HUB-HOST>`、`<LAN-CIDR>`、`<EDGE-PORT>`、`<agent-a>`。

> 结论先行：**同机多会话不需要 hub；同 LAN 不需要证书；跨网络只需要一次出站连接 + 一次注册码**。

---

### 场景 1：单机多会话

- **环境**：一台机器，一个 DSH 进程里跑多个会话；没有其他机器参与。
- **能做什么**：
  - 会话之间互相派活、收回执（`/mesh/inject` + 任务回执）；
  - 批次派活（同一个 `batchId`，全部结束才通知一次）；
  - 会话发现、归档/删除、按标题或 id 定向投递。
- **降级成什么**：不降级——这是最小可用形态，毫秒级、离线可用；
  但**只有同机**，不能把消息发给另一台机器。
- **需要准备**：只需要 waker 插件（`standalone` 模式，监听本机 loopback）；
  **不需要 hub、不需要 token、不需要证书、不需要开任何端口**。
- **不适用**：需要跨机器、需要消息持久化（关机后还能补收）时——那要 hub。
- **该场景不需要什么**：不需要 hub，不需要网络配置，不需要凭据。

### 场景 2：家庭 / 小型局域网

- **环境**：一台常开主机（小主机、树莓派、常开的笔记本都行）+ 2~5 台工作机，同一 `<LAN-CIDR>`；
  没有公网入口。
- **能做什么**：
  - 全部消息能力：收件箱、会话、黑板、blob（大文件中转）、审计；
  - 派活与回执、批次屏障；跨机交接（`skills/handoff` 的 bundle 走 blob）；
  - 开机补收：对方关过机也能收到离线期间的消息。
- **降级成什么**：基本不降级；延迟取决于唤醒方式：
  - 有 `advertiseHost`（LAN 可达）→ push 唤醒，通常十几秒内起一轮；
  - 没有 → pull 轮询，常态 30s、有消息后 5s；
  - 大文件走 hub 中转，没有点对点直连。
- **需要准备**：hub 跑在常开主机上（监听 LAN 地址）、每台机器一个 token；
  **不需要证书**（同 LAN 明文可接受，前提是整段链路你控制）、**不需要端口映射**、**不需要域名**。
  为什么 LAN 内可以明文：威胁模型假设同一网段可信；一旦有访客网络或不可信设备，按场景 3 处理。
- **不适用**：机器分布在不同网络；或者 LAN 内有不可信设备却又不打算加密。
- **该场景不需要什么**：不需要 TLS、不需要公网 IP、不需要注册码（token 可由管理员直接发）。

### 场景 3：云主机 + 多机（跨网络）

- **环境**：hub 跑在有公网 IP 或域名的云主机上，工作机分布在不同网络（家里、公司、移动网络）。
- **能做什么**：与场景 2 相同，另外：
  - 任何能出站访问 `<HUB-HOST>` 的机器都能接入；
  - 注册码/设备码配对：`hubUrl` + `joinCode` 两键接入，自动换 token、自动信任 CA；
  - scopes 按节点收窄（`read / send / board / blob`），`allowed_cidrs` 可选做来源限制。
- **降级成什么**：
  - **没有 `advertiseHost` 时 push 不可用** → 退化为 pull，延迟 = 轮询间隔（30s / 5s / 60s）；
  - 大文件仍走中转，跨网络带宽取决于 hub；
  - `allowed_cidrs` 在反向代理/隧道后面可能失效（源地址会变成代理地址），此时只靠 token + scopes。
- **需要准备**：TLS（自签 CA 或公网证书二选一）、注册码、每节点 token；
  公网只暴露一个入口端口（`<EDGE-PORT>`），管理面默认不对公网开放。
- **不适用**：完全不能出站的网络（见场景 5）；要求点对点直连、不想让 hub 看到内容的场景。
- **该场景不需要什么**：不需要给每台机器开入站端口；不需要把管理面暴露到公网；不需要手工抄 token（用注册码）。

### 场景 4：双 NAT / 没有公网 IP

- **环境**：家里没有公网 IP（或多层 NAT），hub 与工作机都在 NAT 后面，机器之间不能互相直连。
- **能做什么**：
  - **pull 模式**：每台机器主动出站拉取收件箱，任何 NAT 后面都能用；
  - 消息、派活、回执、批次、blob、交接都可用（只要都能出站到同一个 hub）。
- **降级成什么**：
  - **push 唤醒不可用**（hub 回呼不到你）→ 延迟 = 轮询间隔，不是即时唤醒；
  - 没有点对点直连，大文件经 hub 中转。
- **需要准备**：
  - 方案一（最朴素）：**所有机器都在同一 LAN 内**，hub 跑在其中一台常开主机上——不需要公网；
  - 方案二：**用一台云主机做中转**（只做消息与 blob 中转，不做 P2P）——只需要这台机器有公网入口，
    其余机器全部出站连它；
  - 端口映射/内网穿透（frp 等）属于可选的加速手段，不是前提。
- **不适用**：要求「点一下就到」的即时唤醒；完全不能访问任何公网中转机的孤立网络。
- **该场景不需要什么**：不需要公网 IP、不需要在路由器上开端口（pull 只需要出站）、不需要 P2P/打洞。

### 场景 5：企业受限网络

- **环境**：出站只允许 443，禁止入站，强制 HTTP 代理，可能还有企业 CA/拦截。
- **能做什么**：
  - 只要能用 HTTPS 出站到 `<HUB-HOST>`，就能以 **pull** 模式接入：收消息、派活、回执、blob 中转；
  - 通过标准代理（`HTTPS_PROXY` 环境变量）出站；
  - hub 使用公网可信证书时，客户端不需要额外配置 CA。
- **降级成什么**：
  - push 不可用（无入站）→ 延迟 = 轮询间隔；
  - 企业代理做 TLS 拦截时，需要把企业 CA 加进信任链，否则会报证书错误；
  - 自签 CA 在受管机器上可能无法安装 → 优先让 hub 用公网可信证书。
- **需要准备**：出站 443、代理地址、必要时企业 CA；**不需要入站、不需要管理员权限开端口**。
- **不适用**：出站也被白名单限制、只能访问内部服务；或者禁止一切外部消息通道（合规要求）——这类环境
  不要绕过管控，改用内部部署的 hub（在允许的网段内）。
- **该场景不需要什么**：不需要入站端口、不需要 P2P、不需要在受管机器上装驱动或改防火墙。

## 快速对照

| 场景 | hub 在哪 | 唤醒方式 | TLS | 需要开端口 |
|---|---|---|---|---|
| 单机多会话 | 不需要 | 本机注入（毫秒级） | 不需要 | 不需要 |
| 家庭 LAN | 常开主机 | push（LAN 可达）或 pull | 不需要 | 不需要 |
| 云主机 + 多机 | 云主机 | push（有 advertiseHost）或 pull | **必需** | 只需一个入口端口 |
| 双 NAT | LAN 内主机或云中转 | 只能 pull | 视中转机而定 | 不需要 |
| 企业受限 | 公网可达的主机 | 只能 pull（+ 代理） | 建议公网证书 | 不需要 |
