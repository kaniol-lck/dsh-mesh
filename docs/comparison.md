# 与相似方案的对比

一句话定位：**dsh-mesh 是「常驻的消息与派活中枢」，不是编排引擎、不是任务队列、不是网络层。**
下面的对比只回答两件事：它解决什么、什么时候不该用它。

| 方案 | 解决的问题 | 与本项目的关系 | 不适用场景 |
|---|---|---|---|
| **MCP 官方（stdio / Streamable HTTP）** | 模型与工具/资源之间的调用协议 | 本项目通过 MCP **暴露** hub 工具（`mesh_send`、`mesh_inbox`…）；传输层用 MCP，跨机协调用本项目的消息层 | 单纯调用本机工具；不需要持久化收件箱与离线补收 |
| **A2A（Agent2Agent）** | agent 之间的任务委派与能力发现协议 | 思路相近：都是「把任务交给另一个 agent」；本项目更偏**消息/收件箱/唤醒**，协议更轻、可自托管 | 需要标准化 agent 卡片、跨厂商互操作、复杂任务状态机 |
| **AutoGen / LangGraph 等编排框架** | 多 agent 的编排、状态机、图执行 | 互补：框架负责**单进程内的编排**，本项目负责**跨进程/跨机器的消息与唤醒** | 复杂 DAG、条件分支、长流程状态管理；这些请用编排框架 |
| **n8n / 工作流引擎** | 可视化流程、触发器、集成连接器 | 不同层：工作流引擎是「事件驱动的自动化」，本项目是「agent 间的信箱 + 唤醒」 | 需要几百个连接器、可视化编排、定时/事件工作流 |
| **Slack / Discord bot 编排** | 人机混合聊天、通知、channel 内机器人 | 相似的用户体验（消息、频道、机器人），但本项目面向 **agent 与 agent**、可完全自托管、支持离线补收 | 需要给人看的聊天 UI、权限/组织管理、移动端推送 |
| **Tailscale / ZeroTier** | 网络层组网（P2P/WireGuard 覆盖网络） | 互补：网络层负责**可达性**，本项目负责**消息语义**（谁发给谁、离线补收、唤醒、回执） | 只想解决网络连通、不需要消息持久化与 agent 级路由 |

## 什么时候选它们，不选我们

- **只需要本机工具调用** → 用 MCP 就够，不需要本项目的收件箱与唤醒；
- **需要标准化的跨厂商 agent 委派** → 先看 A2A；本项目的协议更轻，但生态与标准化程度不如 A2A；
- **需要复杂编排（分支、循环、重试、人工审批节点）** → 用 AutoGen / LangGraph / 工作流引擎；
  本项目只负责「把任务送达并叫醒」，不负责流程控制；
- **需要可视化、几百个连接器** → n8n 一类；
- **需要给人用的聊天窗口、成员管理、推送** → Slack / Discord 一类；
- **只是网络不通** → Tailscale / ZeroTier 一类先解决可达性，再考虑要不要叠消息层。

## 什么时候可以组合使用

- **mesh + Tailscale/ZeroTier**：网络层解决「互相能连」，mesh 解决「消息落库、离线补收、唤醒、回执」。
  两者叠加时，hub 不需要公网入口（覆盖网络内可达即可）。
- **mesh + 编排框架**：框架在一个进程内编排多个 agent 角色；跨机器的那一段交给 mesh——
  例如框架把「需要另一台机器做的子任务」派出去，用回执收集结果。
- **mesh + 工作流引擎**：工作流引擎做定时/事件触发，触发后通过 mesh 把任务派给某个 agent；
  mesh 的回执可以作为下一步的输入。
- **mesh + A2A（未来）**：A2A 做对外能力描述与标准化委派，mesh 做内部投递与唤醒；两者可共存。

## 我们不解决什么（请勿误判）

- **高吞吐任务队列**：没有优先级队列、重试退避策略、吞吐量保证；它是信箱，不是 Kafka。
- **复杂 DAG / 工作流**：没有图执行、条件分支、扇出扇入语义；编排请用专门框架。
- **强一致分布式事务**：消息是「至少一次」投递，可能重复；需要幂等或事务请在上层做。
- **大规模 UI 管理**：控制台面向少量节点与运维排障，不是几百个 agent 的调度台。
- **内容加密**：TLS 只保护传输层，hub 库内明文；需要端到端加密请自行在消息体上加密。
- **网络层组网**：不提供打洞、覆盖网络、路由；需要时用 Tailscale/ZeroTier/frp/VPN 等。
